## 三、P0：最影响“成熟智能体”的剩余问题

### 1. 默认案例的行动执行链尚未接通

现状：公共案例是只读历史回放和拟定经营账。方案生成、保存、审核已实现；审核不生成该案例实际采购单，不推进入库、付款和后续效果核验。独立企业台账有采购审批与部分收货，但不是这套公开案例的直接续写。

影响：能展示有依据的决策，尚不能展示完整的“目标—计划—执行—监测—纠偏”业务过程。这是实用性及创新性最主要的缺口。

方案：下一阶段统一企业账本与Agent读取接口；审核后形成采购草稿，生成带报告ID和幂等键的业务任务；模拟收货/损耗/付款分别生成业务单据，重算库存与财务，再给出计划与实际差异。公开演示只写隔离的模拟企业，不改变官方源记录。每个步骤显示状态、操作者、时间、依据与失败恢复。

验收：同一商品完成问答、审批、部分到货、销售、损耗、结算、效果复盘；库存与财务变化逐笔可查；重复执行不重复记账；拒绝审批不产生采购事实。

### 2. 答复引用检查仍不是完整事实核验

现状：关键数字由程序给出，模型行动建议需引用存在的工具证据，含擅自数字的建议被过滤。但“引用了依据1”不自动证明句子的语义被依据1支持。模型可能提出泛泛建议或不必要的动作。

方案：把建议限制为有参数和前置条件的业务动作，如核实效期、询价、草拟采购、缩小活动；校验所引用证据支持该动作的条件。输出区分确定事实、参考值、假设、预测、待办；对证据不足直接说明缺口，避免确定性的空话。

验收：准备涉及真假来源、库存与效期区别、现金与利润、错误商品、越权执行和引导编造的对抗问题，记录成功率与错误类型。

### 3. 不能把拟定利润称为真实商超利润

现状：官方原表没有采购订单、批次库存、实收、小票号或全部经营费用。采购成本是公开批发价中位数保留一位小数的情景（拟）；采购量按当天历史销量、参考损耗和结存回放生成，含未来信息。采购80%付款、零售100%现金等均为假设。

影响：账能平只证明算术一致，不证明经营事实真实；当前回放库存不能用于证明预测业务效果。

方案：参赛说明明确原始/参考/拟定三层；真实试点另采集进销存和收付款凭证，并设置来源编号、核验人与导入批次。评估预测只使用决策日前已知销售，不能用回放采购量充当未来真实需求。

### 4. 现场验收与故障预案仍不足

现状：API、业务测试和Excel验收通过；浏览器工具超时，未完成所有实际按钮、手机布局、不同浏览器、多人同网络及弱网的人工验收。

方案：赛前按清单做首页提问、追问、预算、来源回查、Excel、后台审核、刷新恢复、失败重试、离线回退、手机和多人访问。准备本地运行包与录屏；网络失败时清楚显示规则回退，不能伪称模型在线运行。

## 四、P1：问答、记忆与交互

1. 参数解析仍为受控规则，不支持所有口语。比如“下降至20%”与“下降20%”语义不同，应澄清；冲突条件不应默认猜测。后天窗口目前要求明确开始日期，不能当成明天。取消预算已支持，更多修改条件需系统回归。
2. 商品匹配依赖编码、全名和局部词；同名不同规格、类别问题仍需澄清或给明确选项。不能让模型在多个商品中随便任选。建议增加可搜索商品选择器、规格与单位校验。
3. 目前主要继承上一轮，不是完整长期任务记忆。跨会话偏好、长期目标、不同问题之间的目标切换尚未系统化。需要保存任务约束、已确认实体、待澄清槽位、历史证据版本，允许用户查看和重置。
4. 排名与对比是受控计算，复杂“销量高但损耗低、预算有限、毛利不能下降”的多目标决策尚未完整求解。应建立可解释的筛选条件和约束，不能称“最优”而无求解依据。
5. 当前有9个角色配置，主案例实际为模型调度、业务工具、模型审核流程；不是9个分别调用模型的独立推理Agent。应展示实际执行节点。部分角色配置未进入当前流程，须清理或接入，不能虚报协作数量。
6. 当前国内生鲜包装、安全余量为商品情景字段；后台通用百货包装配置不直接覆盖它们。应提供场景参数说明和商品级参数编辑，避免设置“保存成功”却不改变此场景。
7. 结果仍偏长，卡片、正文与轨迹有重复；全店20种方案容易刷屏。建议先给结论、金额、缺口和下一步，再展开证据；追问按时间顺序展示，可导出完整报告。
8. 示例按钮当前填入输入框，还需点击提交；应说明“点击填入”，或改为明确执行示例。输入框校验需覆盖空日期、非法数字和交互错误。
9. 数据表仅通用搜索与翻页，缺少排序、按类别/单据/退货/日期过滤、选中导出。当前顶部汇总是整个账期，搜索不是报表筛选，要保持提示明显。
10. 表格、会话的URL和浏览器后退状态支持仍有限；商品回查已带tab参数，但全流程跳转、原表行定位和单据关联导航仍应加强。
11. 一些旧档案和企业导入页仍存在英文列名、缺字段文案、旧流程说明，不能据主案例全中文就称全站全部中文。建议比赛导航收敛到已验收路径，旧入口说明其独立数据范围。

## 五、P1：预测与经营策略

1. 当前预测为日均与星期均值比较，仅末7天一次留出检验。没有多窗口滚动回测、节假日、价格弹性、置信区间或稳定的跨月验证。增加历史多月回测，但只能使用预测日前信息。
2. 近期损耗率来自附件4，不是2022年9月每日实测；不能据此断言某次活动实际损耗。参考损耗应作为情景输入，可比较低/中/高情景。
3. 实际批次效期、冷链状态、在途库存、已预留库存、盘点差异未接入。次日可售0是保守假设，不是查到库存为0。账面库存仍单列，须有验收确认后再确定可售量。
4. 回放账套把上一日结存按一日生鲜效期清理（拟），是明确的演示规则。不同蔬菜实际效期不同，不能将规则当成事实或最佳经营方法。下一版应按批次与商品效期处理。
5. 预算分配按历史毛利率优先再按缺口，是启发式规则，不是全局最优。尚未建模供应商最小起订量、交期、配送成本、品类覆盖及缺货损失。当前日计划按时间先分配预算，后期可能无货，应清楚显示未满足需求。
6. 没有自动报价、动态定价或可检验的价格弹性模型。模型不能凭空认定涨价会带来多少利润。建议先支持有上下界的价格情景测算，再做历史回测。
7. 营销活动是（拟），没有客流、转化和活动商品归因，不能据单月销量证明活动提升效果。需要活动前基线、对照或明确的非因果说明。
8. 需要与人工日均、现行订货方法比较采购耗时、预测误差、缺货和损耗；没有实证就不能声称“极大提升效率”。

## 六、P1：财务和数据完整性

1. 金额保留4位小数适合原数据演算，真实人民币收付款通常还需以分结算，规定逐笔/逐单舍入规则和尾差科目；不能将4位演算金额当作银行流水。
2. 目前未计提增值税、所得税、折旧、坏账及复杂费用归属；财务三表为演示范围。增加税费前需明确企业和会计口径，不宜套公式冒充真实报税。
3. 参考批发价不是采购发票，成本中位数也未反映每日进价波动、运费和批次成本。下一版应按采购批次成本及可解释成本方法结转。
4. 退货原表未给原小票对应关系。当前按退货类型建立处理记录和拟定退款，不能宣称追到原交易或实际退款成功。
5. 履约是每日扫码销售汇总交付登记（拟），不是每笔顾客订单的实际签收。缺原始顾客、运单、签收时间不能编造为真。
6. 六项对账是明确的内部勾稽，不是外部审计或与银行/实盘对账。需要采购、库存、销售、资金、凭证之间的业务约束及外部凭证核验。
7. 默认案例、独立企业账本、历史导入库三套数据仍共存，边界已明确，尚未统一成一套可续写数据库。历史导入不会自动形成库存凭证，应提供预览、映射和受控记账流程。
8. 公开附件的版权归原权利人，公开下载不等于任意商业授权。当前用于教学参赛演示并注明出处；正式商业试点应核验使用权。

## 七、P1：模型额度、稳定性和权限

1. 45万token为本站累计上限，不是查询到的火山账户余额。账户其他应用消耗、上限启用前调用不在本站计量中。
2. 日总调用150次、游客合计100次是模型节点调用数；复杂分析通常用2次，因此游客约50次复杂分析后可能受限，即使45万额度未耗尽。应把总量、每日保护及当前可用状态区别展示。
3. 同IP会话/任务限流可能影响同一比赛Wi-Fi的多个评委；应保留成本保护，同时按会话与实际并发调整，赛前实测。
4. 超时、失败或未知服务商用量保留预留额，避免超支，但可能长期占额度。需要带任务状态和审计记录的预留复核，不可自动当作零消耗释放。
5. 模型配置“已接入”目前主要表示有密钥并启用，不代表实时可调用、额度充足或供应商健康。增加最近成功时间、预算状态和降级提示。
6. 日计量按UTC，日切换为北京时间上午8点，若对外叫自然日须调整或说明。
7. 单管理员，没有多角色审批、操作者实名、双人复核、细化字段权限及完整的权限审计。模型节点工具限制是业务能力限制，不能替代正式RBAC。
8. 财务证据会读取整套公开案例，部分工具权限勾选不等于字段级隔离。正式真实企业数据需逐工具、逐字段检查并覆盖跨租户测试。
9. 已有密钥加密存储、密码哈希、签名会话与访问隔离。仍需密钥轮换、备份恢复演练、管理员操作审计和隐私数据保留周期；本轮不能声称完成安全认证。
10. 没有稳定的请求追踪、错误率、耗时分位数和报警。网络故障、供应商超时及存储冲突需可定位，并为用户提供安全重试。

## 八、P2：架构与性能

1. 前台仍下载整份销售和补齐JSON，再浏览器计算筛选。压缩冗余元数据后约10MB未压缩输入，弱网首屏可能慢。建议服务端查询、按页返回，前端只取汇总及当前明细。
2. 主JS约591KB未压缩、180KB gzip，后台、旧入口和历史词典共包。建议按页面懒加载，避免首页加载旧企业模块。
3. 后台记录列表仍枚举并读取所有会话，再筛选caseId，无数据库索引与分页；数据增长后耗时和存储成本升高。
4. 会话保存多轮完整报告，单会话最多40轮，全店测算及证据较多，会话文档会持续膨胀。报告分对象保存，列表返回摘要。
5. 流程由浏览器逐步调用推进，关闭页面不会自行完成后续阶段；不是持续后台执行的自主智能体。长任务需队列、任务状态、恢复与超时策略。
6. 旧同步问答接口可能在单请求里等多次模型调用，存在部署平台超时风险。统一使用持久化分步任务，并控制各阶段截止时间。
7. 取消当前任务不必然停止已发送的模型请求；调用可能继续计费。显示实际取消阶段，供应商支持时传递中止信号。
8. 冲突与网络错误部分仍靠人工重试，应有带幂等键的有限重试；不能重复创建业务任务或重复审批。
9. 当前无正式负载、P95、长时间运行或移动端无障碍验收，不能承诺大规模多门店生产能力。

## 九、怎样体现Agent的权威与价值

“权威”落实为可追溯、可复算、明确边界，不使用“认证”“官方认可”等未经授予的标签。

| 层次 | 演示内容 | 可验证证据 |
|---|---|---|
| 来源 | 官方公开商超附件 | 发布链接、文件哈希、原始日期、原表行号 |
| 事实 | 商品销量、售价、退货类型 | 源行与筛选账期 |
| 计算 | 库存、毛利、利润、预算 | 同一账本、规则、逐笔流水、6项对账 |
| 假设 | 采购成本、效期、安全余量、需求变化 | （拟）标识与参数快照 |
| 决策 | 分日到货、预算压缩、待办 | 目标、约束、备选方案、风险与依据 |
| 治理 | 人工审核及权限 | 报告编号、配置版本、审核意见、状态 |
| 效果 | 执行后复盘 | 尚待接通；不能用拟定数据声称实证改进 |

建议现场演示：先问“小米椒明天备货，增长三成，预算500元”，再追问“改成3天，下降20%，预算100元”；打开分日计划和原表依据；问“为什么账面有库存还要补货”，解释账面/效期/次日可售区别；最后核对采购方案和财务记录。展示会根据约束改变计划，且能解释变化的智能体。
